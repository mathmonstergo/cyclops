# Knowledge Graph And Retrieval Review - 2026-07-14

## Scope

Read-only review of the KG backend, KG review UI, evaluation integration, document/FAQ indexing, lexical retrieval, and live database health counts. No business content was read into this artifact.

## Confirmed High-Priority Findings

1. The web evaluation client always posts an empty payload, so `use_kg=true` is unreachable from the UI. Default vector and keyword SQL exclude all KG projections.
2. A failed extraction job is returned as a normal response. Both KG entry points show a success toast without checking `job.status`.
3. Relations can be confirmed while either endpoint remains unreviewed or disabled. Disabling an entity does not invalidate usable relations that reference it.
4. KG retrieval checks only the projection status. It does not enforce the current status of FAQ/document/chunk evidence sources.
5. Re-extraction updates entity/relation review rows and accumulates evidence without rebuilding or invalidating an existing usable projection.
6. Extraction performs a synchronous Chat request in the ASGI request path, and there is no job list/status endpoint for operational recovery.
7. A document chunk with zero or one structured child is stored only as `chunk_level=parent`; direct vector and lexical retrieval exclude every document parent.
8. Editing FAQ text marks only `faq_documents` stale. The ready row in `knowledge_chunks` can continue returning old text and an old vector.
9. The GIN `to_tsvector('simple', search_text)` expression index is unused. Runtime lexical retrieval is weighted `ILIKE`, not BM25.
10. The assistant uses unified hybrid retrieval while CLI, WeChat, and MCP still use the legacy FAQ-only vector path.

## Additional Confirmed Findings

* The subgraph endpoint accepts arbitrary review statuses, even though the product contract describes the subgraph as usable-only.
* Candidate persistence and job completion use separate transactions. A completion-status failure can leave saved candidates behind a failed job, making retries unsafe.
* The fenced-JSON extractor counts braces without recognizing JSON strings. A literal `}` inside evidence can truncate otherwise valid JSON.
* An isolated center entity is omitted from the subgraph response because nodes are assembled only from returned relation rows.
* The KG list page can become stranded on an empty page after reviewing the final row of the last page.
* Previous-page placeholder data remains actionable while a new status/type/page request is fetching.
* Evidence source IDs are returned by the API but not shown, copied, or linked by the review drawer.
* Evidence-free legacy/anomalous rows can still be confirmed; the warning does not disable the action and the backend has no evidence gate.
* Subgraph request errors are rendered as an empty-neighborhood state rather than a retriable error.
* The normal FAQ page truncates IDs and has no direct KG action, so an operator cannot reliably supply the full FAQ ID required by the manual extraction popover.
